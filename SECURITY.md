# Security positions

Holly's deliberate security positions and accepted risks, recorded rather than left silent (security-hardening). Each position names its trip-wire: the change that must revisit it.

## Accepted positions

| Position | Why it is acceptable now | Trip-wire |
|---|---|---|
| Sign-in on every route but a reviewed public set | The API under `/api/v1` needs a valid access token, except the probes, `/`, `/status`, `/api/v1/health`, `/api/v1/health/detailed` and the three sign-in routes (login, refresh, logout). Tokens are JSON Web Tokens (JWT) signed with `APP_SECRET_KEY` (at least 32 characters, checked at boot) and decoded with that one algorithm only; refresh tokens rotate and are revoked on use and sign-out (ADR-011). `tests/test_app.py` pins both the route inventory and the public set. | A new public route fails `test_only_the_reviewed_routes_are_open_without_sign_in` until it is reviewed. The Daily Operations Dashboard's ADR-009 assumed network-level access controls in front of the app; whether the App Store places Holly behind equivalent controls is `TBC, re-verify`, and nothing here relies on them. |
| Most writes are open to any signed-in user | As in the Daily Operations Dashboard, only the audit log needs the operator or admin role. Any analyst can run a UDL ingest, upload or delete a procedure, and edit or delete any shift note or timer. Every such write is recorded in the audit chain with the user and address. | Add role and ownership checks to deletes, ingests and other users' notes before anyone outside the operations team is given an account. |
| Tokens live in the browser's `localStorage` | Any script running in the page could read them, so none is allowed to run but Holly's own: the dashboard policy is `script-src 'self'` with no inline script, no `eval` and nothing from another origin; React escapes every value it renders; links from UDL records are offered only for http and https. An access token lasts 30 minutes and a refresh token can be revoked. | Move the refresh token to an `HttpOnly`, `Secure`, `SameSite=Strict` cookie before any third-party script is added or the policy is loosened in any way. |
| `/status` and `/api/v1/health/detailed` are public | `/status` reports each input in `CONFIG_INPUTS` as set or not and its length, never a value. The detailed health read reports whether the database answers, whether UDL credentials are configured (never the values), the version and the environment, and costs one `SELECT 1`. Both sit behind the coarse rate limit. | Never add a field derived from a secret's value. A secret joins `CONFIG_INPUTS` only if it is high-entropy, because its length becomes public. |
| Cross-Origin Resource Sharing (CORS) allows no origin by default | The dashboard is served from Holly's own origin, so `APP_ALLOWED_ORIGINS` is empty and browsers refuse cross-origin reads. Boot refuses the `*` wildcard. | Review each origin added to `APP_ALLOWED_ORIGINS`; credentials are allowed for every origin listed. |
| Rate limits and the assistant cap count in one process | The coarse tier (600 requests a minute per client address on `/api` and `/status`), failed sign-ins (10 per username in 15 minutes), assistant calls (30 per user in 10 minutes) and the daily assistant token cap (`LLM_DAILY_TOKEN_CAP`, 2,000,000 by default, failing closed) live in memory, so a restart resets them. Holly runs one worker in one container, so each counts once. | Before running more than one worker or replica, move the counters to PostgreSQL: each extra process multiplies every limit, the cap, and the background pulls. |
| The coarse limit may count every client together | It keys on the address the server sees. Behind the App Store ingress that may be the ingress's own address for every request (inference: gunicorn trusts forwarded addresses only from `FORWARDED_ALLOW_IPS`, by default the loopback address). Then all analysts share 600 requests a minute; an idle dashboard tab makes about seven a minute (`frontend/src/context/EventTimersContext.tsx`, `frontend/src/pages/Dashboard.tsx`), so roughly 85 tabs. The audit log would also record the ingress address. | Set `FORWARDED_ALLOW_IPS` to the ingress's addresses once the platform confirms them (`TBC, re-verify`). Never set it to `*` unless the container can be reached only through the ingress, or any client could forge its address. |
| The application's database user can change any table | Migrations run at container start with the application's own database user, so it needs schema rights. ADR-005's insert-only permission for the audit log was never enforced by a migration; migration 0017 now refuses every UPDATE, DELETE and TRUNCATE on `audit.audit_log` with a statement-level trigger, and `python -m app.cli.verify_audit` recomputes the hash chain and names the first broken link. The table's owner can still disable the trigger deliberately. | When the POSTGRESQL add-on can provide a second role, run the application as a role that can only insert into `audit.audit_log` and keep the migrating role for migrations. |
| Audit rows written before Holly V0.2 cannot be verified | The Daily Operations Dashboard hashed a timestamp it never stored, so its rows cannot be recomputed; a chain that starts with them reports its first row as the break. Every row Holly writes hashes the stored timestamp and the stored detail. | If the history must be verifiable, record the last pre-V0.2 hash out of band at migration time and start verification after it. |
| The assistant sends operational text to Anthropic | Evaluations, summaries and note polishing send notification fields, procedure text, team chat and analyst notes to the Anthropic API. ADR-006 records all of it as Unclassified. The key stays server-side; replies are validated (structured fields, procedure ids checked against those sent) before they are stored, and rendered as text. | Re-review what is sent before any data source with a different classification or handling caveat is connected. |
| `apt` and `dpkg` stay in the image | They need root, the image runs as uid 10001, and the platform's reference recipe keeps the OS package manager. | Remove them if the image policy scan flags them. |
| The upload content net has blind spots | It decides positively: only readable text (strict UTF-8 without control characters) is scanned with the secret-scan hook's rules, and every other file, UTF-16 included, is refused whatever its name or format, unless `scripts/upload-binaries.txt` pins it. That list is read from HEAD; each entry pins a binary's SHA-256 with a reason, waives only the text requirement, and still has the binary's readable runs scanned; a changed file, a text file, an unused entry or a path listed twice fails the package. Names add defence in depth (environment files, archive extensions and control characters, without regard to case). It cannot see a secret in a shape the hook has no rule for, such as an unquoted GitHub token or a JWT; a secret encoded inside text, such as base64 or a data: URI; or a secret encoded inside an allowlisted binary, which every run names. | Add rules for those token shapes to the shared hook list, through the Foundations baseline owner, before the first such credential exists. Review every change to `scripts/upload-binaries.txt` as a security change. Before allowlisting the first binary from a Windows toolchain, which stores strings as UTF-16LE, scan that view of the binary too. `scripts/test-package-nets.sh` pins every case the net covers. |
| CI actions pinned by tag, not commit SHA | The workflow holds a read-only token and no secrets, and never deploys. | Pin full commit SHAs, each confirmed against the action's GitHub release page, before the workflow gains any secret or any write permission. |

## Relied on from the platform ingress

1. TLS termination: Holly serves plain HTTP inside the container and sets no `Strict-Transport-Security` header of its own.
2. Host-based routing, so a forged `Host` header is never a routing decision inside the app.
3. Normalising or refusing a request that carries both `Content-Length` and `Transfer-Encoding`. The h11 server follows `Transfer-Encoding` and keeps such a connection open, where RFC 9112 asks for it to be closed.
4. Timeouts for slow clients. The app server held idle and trickling connections for 20 seconds and longer in review testing. Holly refuses a body over 11 MiB, so a slow upload is bounded in size, not in time.
