# Security positions

Holly's deliberate security positions and accepted risks, recorded rather than left silent (security-hardening). Each position names its trip-wire: the change that must revisit it.

## Accepted positions

| Position | Why it is acceptable now | Trip-wire |
|---|---|---|
| Sign-in on every route but a reviewed public set | The API under `/api/v1` needs a valid access token, except the probes, `/`, `/status`, `/api/v1/health`, `/api/v1/health/detailed` and the three sign-in routes (login, refresh, logout). Tokens are JSON Web Tokens (JWT) signed with `APP_SECRET_KEY` (at least 32 characters, checked at boot) and decoded with that one algorithm only; refresh tokens rotate and are revoked on use and sign-out (ADR-011). The access token is read from `X-Holly-Token` alone, never from `Authorization`, a cookie or the query string (ADR-013). `tests/test_app.py` pins both the route inventory and the public set. | A new public route fails `test_only_the_reviewed_routes_are_open_without_sign_in` until it is reviewed. The Daily Operations Dashboard's ADR-009 assumed network-level access controls in front of the app; whether the App Store places Holly behind equivalent controls is `TBC, re-verify`, and nothing here relies on them. |
| Most writes are open to any signed-in user | As in the Daily Operations Dashboard, only the audit log needs the operator or admin role. Any analyst can run a UDL ingest, upload or delete a procedure, edit or delete any shift note or timer, and follow or unfollow a Mattermost channel for everyone (ADR-015). Every such write is recorded in the audit chain with the user and address. | Add role and ownership checks to deletes, ingests and other users' notes before anyone outside the operations team is given an account. |
| Tokens live in the browser's `localStorage` | Any script running in the page could read them, so none is allowed to run but Holly's own: the dashboard policy is `script-src 'self'` with no inline script, no `eval` and nothing from another origin; React escapes every value it renders; links from UDL records are offered only for http and https. An access token lasts 30 minutes and a refresh token can be revoked. | Move the refresh token to an `HttpOnly`, `Secure`, `SameSite=Strict` cookie before any third-party script is added or the policy is loosened in any way. |
| Holly reads every Mattermost channel its bot is in | Since V0.12 Holly finds the bot's channels itself on every Mattermost cycle and follows each new one at once (ADR-015), where before it read only the channel ids `MATTERMOST_CHANNEL_IDS` named. So whoever adds the bot to a channel, public or private, decides that Holly pulls it and that every signed-in user of Holly can read it on the Comms page, and that the assistant reads it as soft context. The bot reads only channels it is a member of (`/users/me/teams/{team_id}/channels`); direct and group messages are never recorded or pulled; a channel named CLOSED or archived yields nothing more; each new channel is flagged on the Comms page until someone reviews it; every follow change is audited with who made it; and Holly only reads Mattermost, never posts. Channel names and Mattermost's values are checked at the boundary, and the page shows them as text. | Revisit before any channel's content must be kept from some Holly users, before the bot joins channels outside the operations team's own, or before Holly writes to Mattermost. |
| The channel sweep's caps limit what is stored, not what is read | Accepted (ADR-015). Fact: the caps of 100 teams and 1,000 channels are checked after each listing is fetched and decoded, so one listing's size is bounded only by the Mattermost server, which Holly trusts as the team's own. A sweep over the caps fails and changes nothing. | Revisit if the bot is added to a Mattermost server outside the operations team's control, or if a listing's size ever needs bounding, by paging the listings. |
| The bot added to a private channel by mistake | Accepted gap, with a remedy (ADR-015). Inference: the bot is a member of a channel because someone in Mattermost added it, and Holly has no way to tell a mistaken addition from a meant one, so it follows the channel at once and every signed-in user can read what it pulls. The remedy, in the operator manual section 06: anyone signed in switches the channel off on the Comms page, which stops the pull for everyone and is audited; the Mattermost admin takes the bot out of the channel, which Holly shows as **Bot removed**. Switching it off also stops what was pulled from it reaching the assistant at once. What was already pulled stays in Holly's database and on the Comms page; removing it needs the database (`DELETE FROM mattermost_message WHERE channel_id = ...`), TBC, re-verify whether the platform gives that access. The first sweep follows every channel the bot is already in, so the operator manual asks for its memberships to be checked before the first deploy. | Revisit if a mistaken addition happens, before the bot joins channels outside the operations team's own, or if pulled messages must be removable from the Comms page. |
| Holly's token header gets none of the care intermediaries give `Authorization` | The access token travels in `X-Holly-Token`, since the App Store's gateway refused it in `Authorization` (ADR-013). A shared cache does not store the answer to a request carrying `Authorization` unless told it may (RFC 9111, section 3.5), and proxies and log tools commonly redact that header; neither holds for `X-Holly-Token`. Holly's `Cache-Control: no-store` on every response, pinned by its tests, is now the only shared-cache protection for a signed-in answer. Whether the gateway logs request headers, and so the token, is `TBC, re-verify`; a logged access token is usable for its lifetime, 30 minutes by default. | Never relax `no-store` on an API response. Ask the platform team whether the gateway logs request headers; if it logs `X-Holly-Token`, have it redacted before Holly holds data above its present classification. |
| `/status` and `/api/v1/health/detailed` are public | `/status` reports each input in `CONFIG_INPUTS` as set or not and its length, never a value. The detailed health read reports whether the database answers, whether UDL credentials are configured (never the values), the version and the environment, and costs one `SELECT 1`. Both sit behind the coarse rate limit. | Never add a field derived from a secret's value. A secret joins `CONFIG_INPUTS` only if it is high-entropy, because its length becomes public. |
| Cross-Origin Resource Sharing (CORS) allows no origin by default | The dashboard is served from Holly's own origin, so `APP_ALLOWED_ORIGINS` is empty and browsers refuse cross-origin reads. Boot refuses the `*` wildcard. Since V0.9 no origin gets credentials mode: Holly reads no cookie, its token travelling in `X-Holly-Token` (ADR-013), and the `_appstore_app_session` cookie travels on requests to Holly's host (seen 20 October 2026; the platform's, by inference from its name), which credentials mode would let a listed origin's calls carry. `tests/test_app.py` pins it. | Review each origin added to `APP_ALLOWED_ORIGINS`. Keep credentials mode off unless Holly comes to read a cookie. |
| A CORS preflight leaves before the security headers, the request id and the coarse limit | CORS is the outermost layer (SonarQube S8414), so it answers a preflight, an OPTIONS request carrying `Access-Control-Request-Method`, before the inner layers run: the answer is a constant `OK` or `Disallowed CORS ...`, a 400 while `APP_ALLOWED_ORIGINS` is empty, reflects nothing the client sent but an allowed origin, touches no database, sign-in or body, and is kept by no shared cache, as RFC 9110 holds for OPTIONS; the browser keeps an allowed origin's answer for the 600 seconds `Access-Control-Max-Age` gives. It carries no CSP, `nosniff`, `Cache-Control` or `X-Request-ID`, and the coarse limit does not count it. Every other response, a 413 or a 429 included, carries the headers and the id, and every request that reaches a route is still counted. `tests/test_app.py` pins both sides: the preflight's fixed body, no request header echoed, no CSP and no request id, and a 429 carrying the CORS headers. Revisited for V0.9, whose `allow_headers` names `X-Holly-Token` in place of `Authorization`: still an explicit list that echoes nothing, and `tests/test_app.py` pins it, allowing `X-Holly-Token` and refusing `Authorization`. | Revisit if a preflight answer ever carries a body worth sniffing or framing, if the coarse limit becomes the only defence against a flood at the ingress, if Starlette's preflight handling changes, or if `allow_headers`, `allow_origin_regex` or `max_age` changes, since `allow_headers=["*"]` would make Starlette echo `Access-Control-Request-Headers` (today it is an explicit list). |
| The first admin comes from platform variables | At start, the gunicorn master counts `app_user`'s rows under an advisory lock. Only while there are none does it read `ADMIN_USERNAME`, `ADMIN_PASSWORD` and `ADMIN_EMAIL`: it checks each before any value reaches a query, refusing half a pair, a password under 12 characters or not valid UTF-8, and a username or email Holly cannot store or that is not printable, then creates one admin with an `auth.user.admin_bootstrap` audit row. Once any account exists no value is checked or used, so none can reset a password, recreate a deleted admin or stop a start; a password of spaces alone counts as unset. A refusal names the variable, never its value; both engines hide every failed statement's bound values (`hide_parameters`). The master drops `ADMIN_PASSWORD` from `os.environ` and from gunicorn's `cfg.env_orig` before the worker forks, but the environment block each process started with (`/proc/<pid>/environ`, readable by Holly's own user) keeps it until the app restarts without the variable, and it sits in the App Store's variable store for as long as it is set. Whoever can set the variables before the first start chooses the admin. | Remove all three variables from the App Store once the admin exists, then restart. Revisit if the app's variables become readable by more than its owners; if any path ever empties `app_user` on a live database, which would re-arm the bootstrap; or before adding any CHECK, exclusion or NOT NULL constraint on `app_user` that an outside value could break, since PostgreSQL's own error detail (`Failing row contains ...`) would print the row, hash included, whatever `hide_parameters` hides: check such a value in Python first. |
| The DAST scan's start relaxes the refusals it would otherwise hit | The App Store's DAST scan runs the image with `APPSTORE_DAST_SCAN=true` and none of Holly's settings (the platform's scan log, 19 October 2026). Under that flag alone the master generates a throwaway `APP_SECRET_KEY` (48 random bytes from `secrets`, never logged) when none is set, a temporary procedure store when none is configured, and turns the background pulls off; and the settings may then lack a database, each request that needs one answering 503. A key or store that is set is kept, half a set of database settings is still refused, and the flag changes nothing else. The flag's name is read in any letter case, as the settings read every name. One `dast_scan` log line names what was set, so a live start that carries the flag by mistake shows it at once: with every setting present it only turns the background pulls off, but it still fills in a missing key (instead of refusing to start) and a missing store (a temporary one, lost at restart; on the App Store the FILE_STORAGE add-on always sets `STORAGE_MOUNT_PATH`). | Revisit if the platform ever sets the flag outside its scan, gives the scan real data, or names it differently; never set it by hand. |
| The database connection is not encrypted inside the platform | The POSTGRESQL add-on's `DATABASE_URL` carries `sslmode=disable` (the console, 19 October 2026), and Holly honours it, so queries and their results cross the platform's internal network in clear, and the password too if the add-on authenticates with a cleartext method (its method is `TBC, re-verify`). The add-on's host, `appstore-holly-postgresql`, reads as a name inside the platform's own network (inference, not confirmed). | Revisit if the add-on offers TLS, if the database or Holly moves outside one cluster network, or if data above the cleared markings is stored. |
| Rate limits and the assistant cap count in one process | The coarse tier (600 requests a minute per client address on `/api` and `/status`), sign-in attempts (30 a minute per client address, counted before any password is checked), checked sign-ins (10 per username in 15 minutes, each counted before its check, a success clearing the count), assistant calls (30 per user in 10 minutes), channel sweeps on demand (6 per user a minute) and the daily assistant token cap (`LLM_DAILY_TOKEN_CAP`, 2,000,000 by default, failing closed, each call's largest possible cost held before it is sent) live in memory, so a restart resets them. Holly runs one worker in one container, so each counts once. A sign-in flood no longer restarts the worker: bcrypt runs on worker threads, at most 4 checks at once, and a sign-in beyond them gets 503 at once (`tests/test_auth.py`, `TestSignInUnderLoad`). | Before running more than one worker or replica, move the counters to PostgreSQL: each extra process multiplies every limit, the cap, and the background pulls. Persist the sign-in throttle too if anything is found that can restart the worker on demand. |
| The per-address limits may count every client together | They key on the address the server sees. Behind the App Store ingress that may be the ingress's own address for every request (inference: gunicorn trusts forwarded addresses only from `FORWARDED_ALLOW_IPS`, by default the loopback address). Then all analysts share 600 requests a minute; an idle dashboard tab makes about seven a minute (`frontend/src/context/EventTimersContext.tsx`, `frontend/src/pages/Dashboard.tsx`), so roughly 85 tabs. The 30 sign-in attempts a minute would be shared too: anyone who can reach Holly, with no credentials, could spend them with one attempt every 2 seconds and keep every analyst from signing in for as long as they kept it up. The audit log would also record the ingress address. | Set `FORWARDED_ALLOW_IPS` to the ingress's addresses once the platform confirms them (`TBC, re-verify`). Never set it to `*` unless the container can be reached only through the ingress, or any client could forge its address. |
| The application's database user can change any table | Migrations run at container start with the application's own database user, so it needs schema rights. ADR-005's insert-only permission for the audit log was never enforced by a migration; migration 0017 now refuses every UPDATE, DELETE and TRUNCATE on `audit.audit_log` with a statement-level trigger, and `python -m app.cli.verify_audit` recomputes the hash chain and names the first broken link. The table's owner can still disable the trigger deliberately. On the App Store the add-on's `DATABASE_URL` connects as `postgres` (the console, 19 October 2026); whether that role is a superuser, whose reach would extend to every database on that server, is `TBC, re-verify`. | When the POSTGRESQL add-on can provide a second role, run the application as a role that can only insert into `audit.audit_log` and keep the migrating role for migrations. |
| Audit rows written before Holly V0.2 cannot be verified | The Daily Operations Dashboard hashed a timestamp it never stored, so its rows cannot be recomputed; a chain that starts with them reports its first row as the break. Every row Holly writes hashes the stored timestamp and the stored detail. | If the history must be verifiable, record the last pre-V0.2 hash out of band at migration time and start verification after it. |
| The assistant sends operational text to Anthropic | Evaluations, event narratives and note polishing send notification fields, procedure text, team chat and analyst notes to the Anthropic API. A notification, and each manoeuvre record sent with it, goes only when its UDL classification marking is in `ASSISTANT_CLEARED_MARKINGS`, matched exactly, which is `["U"]` until the data owner clears more; any other marking, or none, never leaves Holly (`services/disclosure.py`), and the background cycle evaluates a notice only when its latest publication is cleared. ADR-006 recorded all data as Unclassified with no handling restrictions, but the record the dashboard was built against carried a dissemination-controlled marking, so the JCO feed's notices are not cleared by default. Each background sending writes an audit row. Once a notice or event may have been sent, any failure to store its result or its row stops that phase for the cycle, so at most one sending a phase each cycle can go unrecorded: the one that failed, which the server log names. Procedure text, team chat and analyst notes carry no marking and are sent as before. The key stays server-side; replies are validated (structured fields, procedure ids checked against those sent) before they are stored, and rendered as text; failures reach analysts as fixed messages. | The data owner decides whether the JCO feed's marking may be added to `ASSISTANT_CLEARED_MARKINGS` (`TBC, re-verify`). Re-review what is sent before any marking is cleared or any data source with a different classification or handling caveat is connected. |
| The audit chain has no anchor outside the database | `python -m app.cli.verify_audit` finds any edited, deleted or reordered row, and migration 0017 refuses edits, but someone able to disable the trigger and recompute every later hash could rewrite the history undetected. | Before the audit log is relied on as evidence, publish its newest `entry_hash` outside the database on a schedule, for example to the platform log. |
| Admins manage every account on the Users page | Since V0.10 an admin creates accounts, resets passwords, changes roles and deactivates accounts (ADR-014); every route checks the admin role from the database on each request, and every change is audited with the admin and their address. A password an admin sets is temporary: the admin knows it until the user chooses their own, and Holly refuses that account everything but `/auth/me` and `/auth/password` meanwhile, server-side, with a 403 (`tests/test_app.py` pins which routes answer). The temporary password reaches the user by whatever channel the admin uses, which Holly does not see. An admin cannot reset, demote or deactivate their own account there, the last active admin cannot be demoted or deactivated (counted with the account under one row lock), and no account is ever deleted, since the audit chain names it. Any admin can create another, so every admin is trusted with every account, and so is anyone holding an admin's session: they can reset another admin's password and act as them, audited under that admin's name; create an admin whose password they know, which outlives the stolen session; and demote every other admin, after which only `create_admin` restores one, since the `ADMIN_*` variables apply only while Holly holds no account (operator manual, section 11, for the clean-up). A new username is `a` to `z`, `0` to `9` and `. _ @ -`, so no name can pass for another on the page or in the audit view. `python -m app.cli.create_admin` still creates or resets an admin where a shell is available (`TBC, re-verify` on the App Store). | Revisit before a policy forbids an admin knowing a password, even briefly (then send a one-time link instead); before accounts are deleted; and before a role below admin gains any account route. |
| A session ends when its user's token version moves | Each token carries its user's `token_version`, checked on every request and every refresh. A password change, an admin's reset, a deactivation and `create_admin` on an existing account each raise it, so every token issued before stops at once, the access token included, though it has not expired. Each reads the account again under a row lock before it writes (`services/accounts.py`), and a change refuses if its session ended while it ran, so two such changes at once cannot write the same version; before the lock, a password change running during a reset undid it (V0.10's gates, 8 times in 8), and the container smoke rung now races the two. A change keeps only the session it was made in, with a new pair. A token from before V0.10 carries no version and reads as 0, so it lasts until the first change. Sign-out still revokes only that browser's refresh token (ADR-011). | Every new kind of token must carry and check the version. Raise it on any future change that should end a user's sessions, under the same lock. |
| A locked username's count can be pushed out | Each limiter remembers at most 10,000 keys and drops the stalest, and only a recorded hit takes a place, so a sign-in refused before its check takes none. Checking 10,000 other usernames, about 13 minutes with all four password checks busy and attempts from many client addresses, drops a locked username's count and allows it 10 more guesses. Evicting only unlocked keys would add a scan to every eviction, which a flood of addresses could turn against the coarse limit, which shares the class. | Evict only keys under their limit, with a bounded scan, before Holly trusts forwarded addresses (`FORWARDED_ALLOW_IPS`) or is reachable from beyond the operations network. |
| An on-demand evaluation that cannot be stored goes unaudited | The evaluate route writes its audit row after the evaluation is stored. If storing fails after the call, the request answers 500 and no row records that the notice was sent; the server log records the failure with its request id. With every reply checked for storable text, that takes a database that refuses writes, when an audit row would fail too. Each analyst can cause at most 30 such calls in 10 minutes. | Before the audit log is relied on as the record of every disclosure, commit an audit row before the call and complete it afterwards: a row written in the evaluation's own transaction would fail with it. |
| Reads are not audited | The audit chain records sign-ins, writes, ingests and assistant use. Procedure downloads, shift-log exports, audit-log reads and the analyst behind **Pull from UDL** are not recorded. | Audit downloads and exports before any procedure or log is held under a classification that requires access records. |
| One logical event can span UDL sources | Notices group on `Event_Id`, then the NOTSO number, then the UDL id, whatever their source. The background pull asks for source JCO only; a manual ingest may name any source, and a record from another provider reusing a JCO `Event_Id` would join that event and its narrative. | Add the source to the group key before a second source is ingested in normal use. |
| The manual pull holds its request open | **Pull from UDL** answers when the whole cycle ends: the UDL pull, up to 20 evaluations and up to 20 narratives. An ingress timeout shorter than that ends the request while the cycle may be cut part-way; the hourly cycle picks up what is left. | If the ingress timeout proves shorter than a cycle (`TBC, re-verify`), run the manual pull in the background and have the page poll for its end. |
| Many firing timers can leave a short window no room for the page | Above 600 pixels wide and 480 tall the layout has a fixed height, shared by the header, the firing banners and the page, and each banner grows with its label, which may run to 200 characters. The page's content, its navigation and a notice's Classification field are out of reach once firing timers fill that height: with 22-character labels, from 4 timers at once on a 601 by 481 window, 5 on 640 by 512 (a 1,280 by 1,024 window at 200% zoom), 6 on 760 by 600, 9 on 1,024 by 600 and 12 on 1,024 by 768; with 100-character labels, from 2, 3, 4, 6 and 8; and with 200-character labels, from 2, 2, 3, 4 and 5, or one timer sooner on the 1,024-pixel-wide windows where the label is in wide letters, such as capitals. Below those counts every navigation link can still be scrolled wholly into view. V0.3 lost the page within one timer of the same counts. The page comes back when a banner goes, and a banner goes when someone dismisses its timer, which dismisses it for every analyst within 10 seconds: a one-off timer stops, and a recurring one moves to its next time. Short of that, the analyst can zoom in until the window is 600 pixels wide or 480 tall, where the whole page scrolls. The header never shrinks under the banners, so Sign out stays whole, and every banner's Dismiss button can be scrolled to and pressed: with 9 timers firing, at 601 by 481, 640 by 512, 760 by 600, 761 by 481 and 1,024 by 600, and with a 50-character username at 911 by 512 and 601 by 481. V0.4's counts were measured for its fifth and sixth review rounds, each with the audio banner showing; V0.3's are the V0.4 security gate's. | Seen in use: two or more timers with labels of 100 characters or more firing at once, or four or more of any length; any change to the header, the banners, the shell's height rules or the label limit; or a report that the page vanished under banners. Then cap the banner area at 40% of the window and let it scroll (the gate's tested fix), or let the whole page scroll when banners are many. |
| `apt` and `dpkg` stay in the image | They need root, the image runs as uid 10001, and the platform's reference recipe keeps the OS package manager. | Remove them if the image policy scan flags them. |
| The upload content net has blind spots | It decides positively: only readable text (strict UTF-8 without control characters) is scanned with the secret-scan hook's rules, and every other file, UTF-16 included, is refused whatever its name or format, unless `scripts/upload-binaries.txt` pins it. That list is read from HEAD; each entry pins a binary's SHA-256 with a reason, waives only the text requirement, and still has the binary's readable runs scanned; a changed file, a text file, an unused entry or a path listed twice fails the package. Names add defence in depth (environment files, archive extensions and the agent configuration, without regard to case), and every name must be printable ASCII without a backslash and land unchanged on extraction, so a byte an extractor drops, or reads as a separator, cannot turn a refused name into an accepted one. It cannot see a secret in a shape the hook has no rule for, such as an unquoted GitHub token (a JWT, and a token in Holly's own `X-Holly-Token` header, have rules since V0.9); a secret encoded inside text, such as base64 or a data: URI; or a secret encoded inside an allowlisted binary, which every run names. | Add rules for those token shapes to the shared hook list, through the Foundations baseline owner, before the first such credential exists; offer them V0.9's two rules too. Review every change to `scripts/upload-binaries.txt` as a security change. Before allowlisting the first binary from a Windows toolchain, which stores strings as UTF-16LE, scan that view of the binary too. `scripts/test-package-nets.sh` pins every case the net covers. |
| The upload name net reads names as Info-ZIP does | A zip member can carry a second name in a Unicode Path extra field (0x7075). Info-ZIP and Python use it, while Java and Go read the raw name, so a hand-built zip could show the net one name and land another. The net only judges zips that `scripts/package-appstore.sh` builds with `git archive`, which never writes that field. | Refuse members that carry a 0x7075 extra field before the net judges any zip it did not build. |
| The review record proves the record, not the review | Packaging for upload resolves HEAD once and refuses unless the last line from each gate in `scripts/upload-record.txt`, as committed there, is a PASS on a commit in that commit's history, at or after the version bump, whose upload paths and packaging tools are unchanged since (`scripts/check-reviews.sh`). The record counts only the verdicts committed at or before the commit packaged, so an upload must come from the tip of a local branch, refusing a HEAD that is detached or outside `refs/heads/`, a branch behind its upstream as last fetched, and an upstream that is configured but does not resolve. A FAIL is seen only through the packaged commit's history and its upstream's history as last fetched: a branch with no upstream, such as one just made from an older commit, is not compared, and the run says so, and a clone that has not fetched a later FAIL cannot know it, so fetch before packaging, from the branch the verdicts were recorded on. A FAIL recorded last refuses whatever commit it names, and the record must be printable ASCII and tab, counted before the shell reads it. Git's local replace refs never stand in for the committed record, allowlist or archive, its grafts never stand in for the committed history in the review check or the upstream comparison, its commit-graph file never does in the review check or the baseline check, and a local textconv cannot move the version bump. Each packaging tool that runs must match its committed content byte for byte, whatever git's index says, compared once before the archive is built, so a tool swapped while packaging runs is not caught; the zip must hold exactly the committed files of the commit packaged, byte for byte, read as git archive reads its paths (`scripts/check-package.sh`); but a local filter's command, like any local git setting that runs a program, runs while packaging, after the tools were compared, so it can replace a tool, the nets included, and ship content no check saw; a commit landing while packaging refuses; and every run first removes the last upload zip. `scripts/test-package-nets.sh` has a case for each guard but three, against a record, a moved tree, a changed tool, local git state (index flags, filters, attributes, a textconv, replace refs, grafts, a commit-graph), an upstream, a rehearsal path, the repository's own path or a moving HEAD. The three are the refusal when git cannot read a branch's upstream setting, which the git commands before it already stop, since they read the same configuration; `--no-show-signature` in the bump search, without which a signed bump's id comes out garbled and the history check refuses; and the INT and TERM traps, without which a rehearsal stopped by a signal leaves its unscanned temporary zip beside it, where no run clears it. `docs/AUDIT-LOG.md` records which guards a case turns red only through the refusal's wording, and what refuses in their place. It cannot tell a line a gate returned from one written by hand, and anyone who can commit, write to `.git/` or set the environment packaging runs in can also change the check. A rehearsal (`--rehearsal <file>`, refused in dist/ or below it, compared by inode, and under the upload's name; but a link swapped in after those checks can still move it: a link to a directory put at its path receives it under a temporary name, which a later run clears from dist/ but not from elsewhere, and a link to dist/ put in place of its directory receives it under its own name, which no run clears; neither is ever named appstore.zip), or `git archive` by hand, writes the same bytes without the check, so it covers only the file it writes, when it writes it: the gates and the human confirmation the `deploy-gate` requires before an upload stay the controls, and the record makes their outcome checkable. | Before anyone other than the person who ran the gates can package or upload, or packaging moves to CI, make each verdict verifiable: have the gates write their own lines under an identity the packager checks, such as a signed commit, and protect the record with a branch rule. Bring this history into main with its commits, never squashed, or the reviewed commits leave the history and packaging refuses until the gates pass again there. |
| The upload baseline proves the record, not the handover | Packaging for upload also refuses unless the last line of `scripts/upload-baseline.txt`, as committed at the commit packaged, names a commit in this repository that sets the version it records, in exactly one line, and unless an upload changed since that baseline carries a higher version; it then prints the files that differ (`scripts/check-baseline.sh`). Like the review check, it ignores replace refs, grafts and the commit-graph file, and it is one of the packaging tools compared by content. It cannot tell a line recorded after a real handover from one written by hand: anyone who can commit can name any commit at the same version, a dangling one included, and so choose whether the upload reads as unchanged or bumped. It steers what the gate's window is believed to be, not what the upload holds, which the review check and the nets still judge. | Before anyone other than the person who hands packages over can append to the record, have the line carry evidence the packager checks, such as the zip's full SHA-256 compared with a rehearsal of the commit named. |
| CI actions pinned by tag, not commit SHA | The workflow holds a read-only token and no secrets, and never deploys. | Pin full commit SHAs, each confirmed against the action's GitHub release page, before the workflow gains any secret or any write permission. |

## Relied on from the platform ingress

1. TLS termination: Holly serves plain HTTP inside the container and sets no `Strict-Transport-Security` header of its own.
2. Host-based routing, so a forged `Host` header is never a routing decision inside the app.
3. Normalising or refusing a request that carries both `Content-Length` and `Transfer-Encoding`. The h11 server follows `Transfer-Encoding` and keeps such a connection open, where RFC 9112 asks for it to be closed.
4. Timeouts for slow clients. The app server held idle and trickling connections for 20 seconds and longer in review testing. Holly refuses a body over 256 KiB, or 11 MiB for a signed-in procedure upload, so a slow request is bounded in size, not in time.
5. Passing `X-Holly-Token` through to Holly unchanged, and not logging it (`TBC, re-verify`). The gateway refused Holly's token in `Authorization`, so Holly reads its own header only (ADR-013).
