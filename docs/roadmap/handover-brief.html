A handover the next crew can act on

Handover is a planned new tab in . It helps the mission lead hand each live event to the oncoming crew as a short, sourced story: what happened, what it means and what comes next. A does the heavy reading near the end of the shift, so nothing is sent to an outside AI service.

1 · The problem

Today's handover says what, but not why or what next

At the end of a shift, the mission lead hands the watch to the oncoming crew in the Americas. For each event, the handover is often one line. The oncoming crew then spend the start of their shift rebuilding what the outgoing crew already knew.

3 · Where data comes from

Four sources, all of them read only

Handover adds no new kind of data. Holly already reads three of these sources; the fourth is read today only when someone asks. Holly never writes back to any of them.

NOTSOs Exists

The formal notices that mark an event.

What it is
A is published to the when something noteworthy happens to an object, such as a possible manoeuvre.
How Holly gets it
Holly asks the UDL for new NOTSOs every hour and looks back 120 hours.
What Holly keeps
Each publication as received: NOTSO number, event, objects, times, marking and the full original record.
What Handover uses it for
The backbone of each object's story, and the "what happened" sentence.

Pull of TACREP_NOTSO, source JCO, data mode REAL in services/background_refresh.py; table notification.

Provider manoeuvre records Exists

Each provider's reading of a burn.

What it is
Companies that analyse space data, the (for example NorthStar and KBR), publish how a changed an orbit.
How Holly gets it
From the UDL every 10 minutes, looking back 48 hours.
What Holly keeps
Each record with its before and after figures: , , inclination, longitude and drift.
What Handover uses it for
The provider comparison: where providers agree and where they differ.

Table maneuver; figures read from raw by services/maneuver_facts.py. Key names and units are TBC, re-verify against a real KBR and NorthStar record.

Element sets Changed

Where each object's orbit is.

What it is
An describes an orbit at a moment in time, so Holly can predict where an object will be.
How Holly gets it
Today only when someone asks. New in V0.21: Holly fetches them automatically, but only for objects with a live event.
What Holly keeps
The orbit description and its time (epoch). Holly refuses one that is too old and says so.
What Handover uses it for
The 48-hour look-ahead: crossings, closest approaches and lighting.

Table elset with TLE lines. The earlier automatic pull was removed because nobody used it; the new one is scoped to live objects with a freshness guard.

Mattermost threads Changed

Where analysts and providers talk an event through.

What it is
The team chat. A is a post and its replies. Providers often post their figures here first.
How Holly gets it
Every 60 seconds, from channels the Holly bot is in and that are followed. New: Holly records which thread each post belongs to.
What Holly keeps
Each post: channel, author, time and text. Holly only reads; it never posts.
What Handover uses it for
Provider claims, read by the local model and checked word for word.

Table mattermost_message; the thread id (root_id) sits inside raw today and becomes its own indexed column in V0.19.

Two rules at the door

  • Every value is checked as it arrives. Anything Holly cannot store safely is skipped, never guessed.
  • Holly reads from the UDL and Mattermost and writes back to neither.

5 · The end-of-shift run

Five minutes of reading, done before you sit down to hand over

At times your team sets, for example 40 minutes before each shift change, Holly starts its own language model. It works through the live events in priority order: the most recent change first, then RPO, then the rest. For each one it reads the confirmed chat threads and pulls out each provider's figures. At five minutes it stops. Any event it did not reach is marked template only, so nothing is skipped without you knowing.

The model runs as a with no network and no database access: Holly hands it the text and reads back its answer. It stops when the run ends.

Why a made-up number can't reach your handover

Small language models sometimes invent things. So the model is only allowed to pull figures out, and Holly checks every one before it is used. A figure that is not written in the post it came from is thrown away.

Illustrative posts and figures. NorthStar and KBR are the providers named in the owner's memo.

Planned modules: services/handover/local_model.py (llama.cpp through its Python binding, one quantised, permissively licensed model pinned by SHA-256), extract.py (claims and the three checks), end_of_shift.py (single-flight batch, 5-minute budget, one audit row per run). Results are cached per thread against its newest post id, so a rerun reads only threads that changed.

9 · The Phase 0 trial

Proving the built-in model before we build on it

Before V0.20 ships a language model inside Holly, a short trial answers one question: can a model running on ordinary processors, inside an 8 GiB, 6 CPU box, read a shift's chat threads within five minutes and pull out the providers' figures accurately enough for a handover, with no made-up figure getting through?

The trial runs inside Bluestaq on 5 real threads, against an answer key a mission lead writes first. Each candidate model gets a plain go or no-go. The tools for it are built and tested: they live in Holly's repository under trial/, outside the app itself.

Already proved, with made-up data

A dry run on three made-up threads, with canned replies standing in for a model, breaks every rule once. The tools catch each break:

  • a made-up figure, dropped
  • a provider not on the list, dropped
  • a post from outside the thread, dropped
  • a malformed claim, refused
  • a missed claim, which lowers the found rate
  • a figure swapped between two providers named in one post: the checks keep it, and only the lead's answer key catches it

The trial container also builds, runs its 17 tests and loads the model runtime with the network switched off.

Data handling

  • Real threads, answer keys and results stay on one trial machine inside Bluestaq. None is committed, uploaded or pasted into any outside tool, including an AI assistant.
  • The model runs with the network switched off and reads the data folder without being able to change it.
  • Results hold post ids and figures, never thread text, and are deleted when the trial ends. Only a short summary of pass and fail per mark is kept.

10 · Safeguards and risks

Built so a wrong handover is hard to make

1

Nothing leaves Holly

The model runs inside Holly's container. A test fails the build if any Handover code even imports the outside AI client.

2

Made-up figures are thrown away

Every figure must appear word for word in the post it came from, and the post itself must tie it to a provider on your list.

3

A person links chat to events

Holly suggests which thread belongs to which NOTSO. Only a link a lead confirms is used.

4

You confirm every handover

Nothing reaches the oncoming crew as a handover until the mission lead confirms it.

5

Calculated figures say so

Every look-ahead figure is labelled "from element set, indicative", with its time. It is never presented as observed.

6

It still works without the model

If the model fails or runs out of time, the synopsis falls back to the template, filled with checked data.

7

Providers are never blended

Disagreements are shown side by side. Two providers are never averaged into one figure.

8

Every run is recorded

One audit row per run: events read, claims kept and dropped, time taken.
