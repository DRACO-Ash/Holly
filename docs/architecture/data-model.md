**SECTION 01**

## Schemas and conventions

PostgreSQL hosts two schemas:

● `public`: the operational data Holly reads and writes.
● `audit`: the append-only audit log. Migration `0017_audit_append_only` adds a trigger that refuses every UPDATE, DELETE and TRUNCATE on it. No migration grants or revokes privileges: Holly's own database user runs the migrations and owns the table, so the protection is a trigger, not a permission (ADR-012).

Conventions every table follows, unless its section says otherwise:

● `id` is a universally unique identifier (UUID) primary key, generated by the application (`uuid.uuid4`), not by the database.
● `created_at` and `updated_at` are `timestamptz`, set by the database (`now()`). The ingest upsert sets `updated_at` again on every update, as does an update through the object-relational mapper (ORM).
● Every timestamp is `timestamptz`.
● Tables filled from UDL follow ADR-007: the fields analysts query are typed columns, and the whole UDL record is kept verbatim in a `raw` JSONB column. They deduplicate on UDL's own id, `udl_id`, through a unique constraint that the upsert (`INSERT ... ON CONFLICT DO UPDATE`) targets. A record without an id is skipped and counted.

The migrations are the source of truth for the schema; the SQLAlchemy classes in [src/app/models/](../../src/app/models/) describe the same columns to the application.

### `notification`

UDL notification records. UDL serves Tactical Reports (TACREP) and Notices to Space Operators (NOTSO) through one `/notification` endpoint under `msgType=TACREP_NOTSO`; other message types land here too. The hourly background cycle pulls `TACREP_NOTSO` records with data mode `REAL` and source `JCO`; `POST /api/v1/notifications/ingest` pulls on request. This table replaced the original `notso` table at migration `0005_rename_notso`; migration `0006_notif_msgbody` added the columns taken from UDL's `msgBody` object.

UDL re-publishes the same logical notice many times, and each publication is its own row. The notification list, the dashboard feed and the automatic evaluations show only the latest publication of each logical notice, grouped by `COALESCE(event_id, notso_identifier, udl_id)` ([src/app/services/notification_query.py](../../src/app/services/notification_query.py)).

| `data_mode` | varchar(20) | yes | UDL `dataMode`, for example `REAL`. |
| `source` | varchar(100) | yes | UDL `source`, for example `JCO`. |
| `classification_marking` | varchar(50) | yes | UDL `classificationMarking`. |

| `event_type` | varchar(50) | yes | `msgBody.Event_Type`. Indexed. |

**Constraints and indexes**

● `uq_notification_udl_id`: unique constraint on `udl_id`, the upsert's conflict target.
● `ix_notification_notice_id`, `ix_notification_msg_type`, `ix_notification_effective_from`, `ix_notification_sat_no`: the original query indexes.
● `ix_notification_notso_identifier`, `ix_notification_status`, `ix_notification_event_type`, `ix_notification_publish_date`: added at migration `0006`.

**Querying `sat_ids`**

The list is JSONB. To find every notice that mentions satellite 25544:

```sql
SELECT notso_identifier, event_class, status
  FROM notification
 WHERE sat_ids @> '["25544"]'::jsonb
 ORDER BY udl_created_at DESC;
```

This complements the indexed `sat_no` column, which covers only the single-satellite case.

### `event_timer`

Countdown timers analysts set for upcoming events, with a pre-alert and an optional recurrence. Every signed-in user sees and can act on every timer.

| Column | Type | Nullable | Notes |
|--------|------|----------|-------|
| `id` | UUID | no | Primary key. |
| `event_key` | varchar(200) | yes | Optional event id or NOTSO number. Indexed. |
| `label` | varchar(200) | no | Stored trimmed; must hold a character that is not whitespace. |
| `target_time` | timestamptz | no | When the timer fires; must fall between the years 2000 and 2099. Indexed. |
| `pre_alert_minutes` | integer | no | Database default `5`; the API accepts 0 to 720. |
| `recurrence` | varchar(20) | no | `none`, `daily`, `weekly` or `monthly`. Database default `none` (migration `0014`). |
| `recurrence_anchor` | timestamptz | yes | The first occurrence a recurring timer counts from (migration `0016`). |
| `pre_alert_fired_at` | timestamptz | yes | When the pre-alert was first acknowledged. |
| `dismissed_at` | timestamptz | yes | When a one-off timer was dismissed. Indexed. |
| `dismissed_by` | UUID | yes | Foreign key to `app_user.id`, `ON DELETE SET NULL`. |
| `created_by` | UUID | yes | Foreign key to `app_user.id`, `ON DELETE SET NULL`. |
| `shift_date` | date | yes | Optional shift date. |
| `created_at` | timestamptz | no | Row creation time. |
| `updated_at` | timestamptz | no | Row update time. |

**How a recurring timer moves on.** Dismissing a one-off timer sets `dismissed_at`; it leaves the active list 12 hours later. Dismissing a recurring timer moves `target_time` to its next occurrence after both now and the current target, counted in whole steps from `recurrence_anchor`, and clears `pre_alert_fired_at` ([src/app/api/v1/routes/event_timers.py](../../src/app/api/v1/routes/event_timers.py)). Counting from the anchor, never from the last occurrence, keeps a monthly timer on its own day: one set for the 31st fires on 28 or 29 February and then on 31 March again. Holly sets the anchor to the target when a timer is created. Migration `0016` set it to the current target for every recurring timer that existed, so a timer that had already drifted keeps its drifted day; a timer that still has no anchor counts from its current target and gains one at its next dismissal.

**Indexes:** `ix_event_timer_target_time`, `ix_event_timer_dismissed_at`, `ix_event_timer_event_key`.

## Migrations

All schema changes are Alembic migrations, packaged with the application:

● [src/app/migrations/env.py](../../src/app/migrations/env.py): async-aware. It imports every model, reads the database URL from the settings, and runs each migration session under a PostgreSQL advisory lock (`0x484F4C4C`), so two containers starting together cannot migrate at once.
● [src/app/migrations/versions/](../../src/app/migrations/versions/): one file per migration, `0001_create_elset` to `0017_audit_append_only`, in one linear history.
● [src/app/migrations/columns.py](../../src/app/migrations/columns.py): column groups the migrations share. Frozen, because migrations that have already run import it; a new shape gets a new function.
● [alembic.ini](../../alembic.ini) at the repository root serves the developer's `alembic` command line: `script_location = %(here)s/src/app/migrations` and `prepend_sys_path = %(here)s/src`. The container does not use it.

**In the container**, the gunicorn master applies every pending migration before the worker starts ([src/app/migrate.py](../../src/app/migrate.py), [src/app/gunicorn_conf.py](../../src/app/gunicorn_conf.py)), logging `{"event": "migrations", "status": "starting"}` and then `"applied"`. A migration that fails stops the container, with Alembic's error in the log. A container whose code is older than the database's newest migration also stops here, because Alembic cannot locate the newer revision; see the [operator manual](../runbook/operator-manual.md).

**On a developer machine**, from the repository root, with the settings in the environment or a local `.env`:

```sh
.venv/bin/alembic upgrade head        # apply pending migrations (scripts/dev.sh does this for you)
.venv/bin/alembic current             # the revision the database is on
.venv/bin/alembic downgrade -1        # step back one revision
```

Downgrades drop tables and their data, and downgrading `0017` removes the append-only trigger. Use them on a development database only.

**Adding a migration.** Write it by hand or start from `.venv/bin/alembic revision --autogenerate -m "short message"` (which needs a database) and review the result. Name the file after its revision id, `NNNN_short_name.py` with `revision = "NNNN_short_name"`, and set `down_revision` to the current head. [tests/test_migrations.py](../../tests/test_migrations.py) fails unless the history stays linear with one head, the newest file's name is the head, and upgrading to head builds every table the models describe.
